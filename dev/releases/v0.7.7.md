# Airclone v0.7.7 — the sync preview actually works now

Five bugs from one user session, all on the "mark a folder, sync into it" flow
that shipped in 0.7.6, plus one guard that was closed and quietly reopened.

## What is fixed

- **A sync preview over a real folder no longer gives up.** Comparing two
  locations ran as a single request with a 30-second limit, and a comparison of
  13,356 files does not finish in thirty seconds — so the preview failed on
  exactly the folders big enough to need one. It now runs as a background job and
  checks on it, so there is no deadline to miss.

- **You can cancel it.** A comparison over a large folder runs for minutes, and
  the only way out was to close the window — which stopped you waiting but left
  the work running. Cancel now stops the job.

- **"Sync … to here" no longer looks like it did nothing.** It was reading the
  whole source folder first — every file, recursively — before anything appeared
  on screen. On a large source that is several seconds of a window that has not
  changed, which is indistinguishable from a dead button. It now asks a single
  quick question of the source instead, and both steps say which one is running.

  The thorough check is not gone: it still runs for a one-way Sync you have
  chosen to actually run, where it guards against a source that looks populated
  but contains no files — a case that would otherwise empty the destination.
  It happens after you have said what you want, and you can cancel it.

- **Scrollbars you can see are now scrollbars you can drag.** The list in the
  preview showed a scrollbar that would not move. The same fault turned out to
  affect the "remove all remotes" list and **every text-file preview**, which had
  been un-draggable since it shipped. All three are fixed.

- **Long remote names continue onto a third line instead of being cut.** 0.7.6
  let a name that did not fit continue onto a second, smaller line — but that
  second line was itself capped, so at a narrow sidebar width names like
  `S3-LONGREMOTENAME_RC-DISK-C1` were still truncated at the part that tells them
  apart. The remainder now wraps.

- **A `union` or `combine` remote is no longer assumed safe to read.** The
  download guard added in 0.7.6 treats "I cannot tell" as "might be online-only"
  and asks first. These two remote types were being recorded as "definitely not
  online-only" instead, which skipped the question entirely. They are back to
  being treated as unknown.

## Notes for the curious

The union/combine one is worth explaining, because its test passed the whole
time. The test asserted the right thing — that an unfollowable remote stays
unknown — but built its input by hand in a way that did not match what the app
actually does at runtime. Green for a reason unrelated to the behaviour it
claimed to check. It now builds its input the same way the app does, and it fails
against the old code.

## Verified

- Full suite green: **833 tests**, plus `flutter analyze` and `dart format`.
- Both this release's guards were confirmed to **fail without their fix** before
  being kept — the missing prompt genuinely absent, and the union remote genuinely
  reported as safe. A regression test that has never failed proves nothing.
