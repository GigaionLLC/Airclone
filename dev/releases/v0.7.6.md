# Airclone v0.7.6 — when it isn't sure, it asks

Almost everything here is the same shape: an operation that hid or destroyed
something and reported success. A folder that was full said "empty". A file that
was replaced said nothing at all. The fix in each case is not cleverness — it is
Airclone admitting what it does not know, and asking you first.

## What is fixed

- **Downloading, dragging in, and sending to the other pane no longer overwrite
  silently.** Paste, "Copy to…" and "Move to…" have always asked before
  replacing a file. Five other paths did not: Download (from the toolbar, the
  inspector, and a selection), files dragged in from Explorer or Finder, and the
  ⇄ transfer-to-other-pane button. rclone replaces by default, so a same-named
  file at the destination was gone — no prompt, no warning, nothing to undo.

  All five now ask the same Skip / Replace / Keep both question as the rest, and
  refuse outright when the destination can't be read rather than assuming it is
  empty. The pane-to-pane transfer also stops clearing your selection when you
  cancel, which previously made a cancelled transfer look exactly like a
  completed one.

- **Creating a remote can no longer overwrite one that already exists.** Typing
  the name of an existing remote in either wizard replaced it — no warning, no
  confirmation, nothing in the result to say anything had been lost.

  On an encrypted remote this was silent data loss. The files stayed where they
  were, but a new password or salt cannot decrypt their names, so they were
  skipped and the folder appeared **empty**. Nothing anywhere reported an error,
  and the encryption wizard's own verification step still passed — it only ever
  proved the new key was consistent with itself, not that it could read what was
  already there.

  Both wizards now refuse a name that is taken, and refuse just as firmly when
  the existing remotes can't be listed at all. Editing a remote is unchanged; it
  was always a separate, deliberate action.

- **A folder that looks empty now says why it looks empty.** When an encrypted
  remote's password or salt does not match what its contents were encrypted with,
  rclone cannot decrypt the filenames, so it skips every entry and returns an
  empty listing — successfully. Airclone believed it and drew **"Empty folder"**
  over directories that were full.

  It now reports what actually happened: *"6 items hidden — rclone could not
  decrypt the names"*, and flags a listing that came back only partly short. The
  explanation was always there, in a note rclone writes to its own log that
  release builds discarded.

- **Encrypted and aliased remotes that live on local storage no longer bypass the
  download guard.** Airclone refuses to read the contents of a file that a sync
  folder (Proton Drive, OneDrive, iCloud) is keeping online-only, because reading
  it downloads the whole thing. That guard recognised a plain local folder — but
  not an encrypted or aliased remote pointing *at* one, which is a normal way to
  keep an encrypted vault inside a synced folder.

  On such a remote, the duplicate-file scan was the sharp edge: it skipped both
  the check and the "download these files?" prompt, and went straight to reading
  every file in the folder and everything beneath it, whether or not you had ever
  opened those subfolders.

  Two honest limits. If a remote encrypts filenames, Airclone cannot tell from the
  outside which of its files are online-only — so it now asks once about the whole
  scan and says so, rather than reporting a confident count it never established.
  And a remote configured without a folder of its own could not be checked at all;
  "nothing could be checked" was being treated as "nothing to worry about", which
  is now treated as the unknown it is.

- **Long remote names are readable again.** At the sidebar's width, a trailing
  ellipsis cut names off at exactly the point that distinguishes them — three
  remotes ending `_RC-DISK-C1`, `-M1` and `-O1` all rendered identically. The
  first line now runs to the edge at full size and only the remainder wraps to a
  smaller second line. Names that already fit are untouched.

## New: mark a folder, go elsewhere, sync into it

Right-click a folder → **Set as sync source**, navigate anywhere — another
remote, another pane, days later — then right-click → **Sync … into this
folder…**. It opens the existing transfer options dialog already aimed at Sync,
with the destructive confirmation, filters, `--max-delete` and dry run all
intact. Advanced mode only.

Most of the work here is refusals, because a one-way sync makes the destination
match the source and **deletes everything else**. Until now both ends were picked
in the same glance, side by side. Choosing them minutes apart, from different
places, removes the thing that used to make a mistake obvious — so:

- Overlapping locations are **refused**, not warned about, in both directions and
  regardless of letter case. Syncing a remote's root into a folder inside it, or
  a folder into its own parent, is two clicks with nothing on screen to suggest
  anything is wrong. (`Photos` and `Photos-old` are correctly *not* treated as
  overlapping.)
- A source that is **empty or unreadable is refused**. A one-way sync from an
  empty folder deletes everything at the destination, and "I could not read it"
  must never be mistaken for "there is nothing in it".

## New: importing a config can replace a remote, on purpose

Importing a configuration that contains a remote you already have used to offer
one way out: rename the incoming one. You can now choose **Replace** instead, and
the incoming settings win.

This is the same act the wizards now refuse — and that is the point. `config/create`
overwrites a section rather than refusing it, so the danger was never replacement
itself, it was replacement *nobody asked for*. Here you choose it explicitly, per
remote; the existing configuration is backed up before anything is written, so a
bad decision is one restore away; and the result reports what was replaced
separately from what was created, rather than folding both into "imported".

## New: remove every remote in one action

Settings gains a **Remove all remotes** action. Clearing out a configuration you
no longer want previously meant confirming each remote separately — sixteen
times, in a list you were halfway through editing.

It backs the configuration up first, and if it cannot find the active config file
to back up, it **refuses** rather than proceeding: without a backup this is not
recoverable. The confirmation has to be acknowledged before the button does
anything.

## Notes for the curious

None of this required an unusual setup to be *possible*, but it did require one
to actually happen: an encrypted remote has to sit on local storage for the guard
to matter, and most point at cloud storage instead, where there is nothing to
download twice. Checked against a real configuration with nine such remotes, none
of them qualified. This is a hole that was open, not one that was being fallen
into.

If a remote of yours already shows as empty and you believe it is not, this
release does not repair it — the data is intact and the configuration is what is
wrong. The remote's password and salt no longer match what its contents were
encrypted with. Correcting that entry in your rclone configuration brings the
files back; nothing was deleted.

## Also in this release

- The iOS release lane no longer authorises Xcode to create signing certificates
  on its own during export. It only ever needed that for one deliberate
  experiment, and leaving it on the shipping path is how ten unused certificates
  accumulated against Apple's account limit.
- The bundled rclone engine remains **1.75.1**.

## Verified

- Full suite green: **790 tests**, plus `flutter analyze` and `dart format`.
- Both new guards were confirmed to **fail without the fix** before being kept —
  the download prompt genuinely absent, and `config/create` genuinely firing on a
  name that already existed. A regression test that has never failed proves
  nothing.
