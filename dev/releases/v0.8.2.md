# Airclone v0.8.2 — Linux gets a real install, and two backup fixes worth reading

Linux has only ever had a `.tar.gz` of loose files. It now has an **AppImage** and
a **Flatpak**, both with a menu entry and an icon. Alongside that, two fixes to
backup that affect what actually lands on your storage, and QR import on a Mac.

## Linux: three ways to install

| Download | What it is |
| :--- | :--- |
| `Airclone-x86_64.AppImage` | One file. Make it executable and run it — it carries its own libraries, so nothing needs installing. **Start here if you are not sure.** |
| `airclone.flatpak` | `flatpak install --user ./airclone.flatpak`. Appears in your software centre and updates like any other app. |
| `airclone-linux-x64.tar.gz` | The raw files, unchanged, for packaging it yourself. |

The rclone engine is inside all three; there is nothing to download on first run.

This is not only about convenience. The tarball links libraries a desktop may not
have, and on a clean Ubuntu 24.04 it does not start at all — it stops at
`libsecret-1.so.0`, `libmpv.so.2` and `libasound.so.2`, leaving you to work out
three package names from a linker error. The AppImage carries them.

Two deliberate choices you may notice:

- **The AppImage uses your system's audio libraries when you have them**, and
  carries a last-resort copy only for machines that have none. Replacing a
  working ALSA would break your machine's own sound setup rather than help it.
- **The Flatpak cannot mount a remote as a drive**, and says so if you ask it to.
  That is not a permission you can grant: a Flatpak has its own view of the
  filesystem, so a drive mounted inside it would be visible only to Airclone and
  not to your file manager — which is the entire point of mounting one. Use the
  AppImage or the tarball if you need mounting.

Linux now uses the same application identifier as Android,
`com.gigaionllc.airclone`, so the window, the icon and the desktop entry all
agree with each other.

## Backup: two fixes that change where files go, and what runs

**Every Android phone was backing up into the same folder.** The backup wizard
took the per-device folder name from the system host name, which on Android is
the constant `localhost` — so two phones backing up to one cloud remote wrote
into `Airclone/Backups/localhost/` together. The device segment exists precisely
to stop that, and the first sign of it going wrong is a restore putting one
phone's files on another. Android now asks the platform for the real device name,
which is what camera-roll backup always did.

*If you already have a backup task on Android*, it keeps its stored destination —
your existing backups are not moved or orphaned, and nothing is deleted. A backup
you create from now on gets a folder named after the device.

**The Run button ignored a backup's safety rules.** A backup is copy-only, keeps
replaced files as versions, and never runs as a dry run — and those rules are
re-applied every time a *scheduled* run fires, so that a task edited in the
advanced dialog cannot run as something other than what its name says. Pressing
**Run** by hand skipped that, so a backup whose mode had been changed to Sync
would run as a sync, deleting at the destination to match the source. It now
applies the same rules as every other way of running it.

## Scheduling: it was telling some people the opposite of the truth

On Android, the "Also run while Airclone is closed" checkbox explained that it
registers *a Windows Scheduled Task* and that missed runs start *as soon as the
PC is available*. The Saved tasks panel separately insisted scheduled tasks "run
only while Airclone is open" — false on exactly the two platforms, Windows and
Android, where they do not. Both now say what is true for the device you are on.

## A user guide

There is now a proper guide at [`docs/guide/`](../../docs/guide/) — eleven pages
covering browsing, transfers, backup, scheduling, camera-roll backup, mounting
and sharing, moving your remotes between devices, the command console and
troubleshooting. It is written for someone using the app, and every claim in it
was checked against what the app actually does.

## Also

- **Import a QR config with a Mac's camera.** QR import was phone-only on the
  reasoning that a computer has no camera. A MacBook has one. The
  direct-download macOS build now scans live; the Mac App Store build is
  unchanged and still imports from a picture.
- Fresh screenshots in the README, taken against this release.

## Verified

- Both Linux packages are built **and run** in CI before publishing: the AppImage
  is extracted and launched under a virtual display, and the Flatpak is installed
  exactly as a user would install it and then launched.
- The AppImage was additionally taken apart on a machine with none of the
  libraries installed, to confirm they are genuinely inside it rather than merely
  resolvable on the build server.
- Full suite green: **1,147 tests**, plus `flutter analyze` and `dart format`.

## Notes

- Windows builds are signed (Azure Artifact Signing); macOS builds are Developer
  ID signed and notarized; Android is release-signed. The Linux packages are
  unsigned, as Linux packages from a single developer usually are.
- The Flatpak is built for direct installation. It is not a Flathub submission:
  that needs a source build and an application ID tied to a domain, neither of
  which applies to a downloaded bundle.
- Mounting remains unavailable in the Flatpak and the Mac App Store build, for
  the sandbox reasons above. Every other package has it.
