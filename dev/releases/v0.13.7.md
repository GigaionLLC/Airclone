# Airclone v0.13.7 — typing works on Linux

## If you use Airclone on Linux, you could not type in it

Not in the filter, not in the address bar, not in a dialog. Clicking worked
perfectly, which made it look like something about your machine.

It was not your machine. **Every Linux build since v0.10.0 has been like this**,
in the AppImage, the tar.gz and both Flatpaks. Airclone applied a window effect
at startup through a plugin whose Linux version hides the window and the app's
own view and then shows them again — and a view that has been hidden stops
receiving the keyboard. Nothing gave it back. Clicks kept working because a
click goes to whatever is under the pointer, whether or not anything has
keyboard focus.

Airclone no longer applies that effect on Linux, where it never did anything in
the first place: the two effects it offers are Windows 11 materials, and on
Linux every setting resolved to "no effect", which is what the window already
is. The app also takes the keyboard back whenever its view reappears, so nothing
like this can happen quietly again.

This was reported from WSL. It had nothing to do with WSL — it happens on any
Linux desktop, and it now has a test that types into a real window on every
build and fails if the keys do not arrive.

## `--webui` opened a window, on Linux and macOS

`--webui` serves the interface to a browser instead of opening a window, which
is the point of it — for a machine you are not sitting at. It opened an empty
window anyway and left it there for as long as the server ran, with a Dock icon
on macOS.

Both are fixed. On Linux the window is never shown; on macOS the app now runs
without building one at all.

**On Linux it still needs a display**, even though it shows nothing on one. On a
machine with no display, run it against a virtual one:

```
sudo apt install xvfb
xvfb-run -a airclone --webui
```

Run it without either and it now says that, and names that command, instead of
failing with a display error.

## `--version` never answered on macOS

`Airclone.app/Contents/MacOS/Airclone --version` printed nothing and did not
exit. It was trying to start the whole app to answer one question. It now
answers immediately, as it does on Windows and Linux, and `--help` with it.

## The Flatpak was built on a runtime that had expired

Installing it warned: "The GNOME 48 runtime is no longer supported as of March
24, 2026." It now builds on GNOME 50. Nothing about the app changed; it is the
platform underneath it.

## A problem report now says which build it came from

Settings → Diagnostics → **Problem report** gains one line naming the package:
`AppImage`, `Flatpak (Flathub)`, `Flatpak (release bundle)`, `Snap`, `tar.gz`,
`MSIX package`, `installer`, `portable zip`, `app bundle` — or, on a phone,
tablet or TV, which of those it is and the window size. One platform ships
several packages that fail in different ways, and "the Linux build" cost a round
trip on every report.

No device name, model or serial. Knowing it is a tablet is useful; knowing whose
is not.

## Smaller things

- **The update check said you were up to date when you were not.** It asked
  whether the newest release tag contained your version, and `v0.9.10` contains
  `0.9.1`. It now compares versions properly.
- **`--log-input`** is new: run Airclone with it and every key press prints one
  line saying what arrived and whether a text field had focus to receive it. It
  is what found the bug above, and it is there for the next one.
- The startup noise on a machine with no sound card (`ALSA lib ...`,
  `CRITICAL: Failed to create AudioController`) is explained in the
  troubleshooting guide. It is harmless, and it comes from the media plugin
  looking for a mixer that is not there.

## Notes

- Windows builds are signed; macOS builds are Developer ID signed and notarized.
- This release is on GitHub only and has not been sent to any app store.
- Not tested on real hardware: mounting from the Flatpak with the permission
  granted, and mounting on macOS at all. Both are covered by automated tests
  only.
