# Airclone v0.13.3 — the iPhone could not import a config, and the Web UI was downloading your cloud

Two reports, one from [issue #5](https://github.com/GigaionLLC/Airclone/issues/5)
and one from a user running v0.13.2 on Windows. Both turned out to be bigger than
the symptom.

## Importing a config on iOS failed, whichever way you tried it

> "I'm attempting to import my config file into the iOS app. I've tried using
> both the QR code method and the Airclone encrypted file method. This is what
> happens regardless of which import method I use."

Neither import method was at fault. Both end at the same step, and that step
looked for your active config file by **running rclone as a separate program** to
ask it. iOS does not allow an app to start another program at all, so the lookup
came back empty and the import stopped with `Couldn't locate the active config
file to replace`.

Airclone already knew where the file was. On iPhone, iPad and the Mac App Store
build it keeps the config at a fixed place inside the app's own storage, exactly
so it never has to ask. That is now what the import uses.

**This was never only about importing.** The same lookup sits behind config
backup, restore, merge, "remove all remotes" and "export an exact copy" — all of
which were failing the same way on iOS and on the Mac App Store build. They work
now. If you are on a fresh install with no config yet, that is fine: the import
creates one.

## The Web UI was downloading your online-only files

Opening a folder of cloud files in the Web UI could pull **hundreds of them down**
from Proton Drive, OneDrive or iCloud, silently, just from loading the page. The
same folder in the desktop app was fine.

A browser cannot see your computer's filesystem, so it could not tell which files
were online-only placeholders — it did not draw the cloud badges, and it asked for
a thumbnail of everything it saw. Each of those thumbnails forced a download.

Now the **computer serving the page** answers that question, on the file list your
browser is already fetching, so:

- Online-only files and folders show the cloud badge in the Web UI, like the app.
- No thumbnail, preview or checksum will fetch a file that is not on the disk.
- Opening one still works. You get the same "this file is stored online only"
  notice, and downloading it stays a thing you choose.

Checksums and the duplicate finder were fetching them too, and no longer do.

## Drag and drop into the Web UI did nothing

Dragging files from your desktop onto the Web UI showed a "copy" badge and then
silently did nothing at all. It was reading the dropped file's location on disk,
which a browser never provides — deliberately, for your privacy — so it ended up
with nothing to upload and said so to nobody.

It now reads the file itself. Dragging from the app on the same machine still
takes the faster route, where the host copies the file directly.

## Upload and Download buttons, and readable text

- **Upload** and **Download** now sit in the Web UI toolbar next to Cut, Copy and
  Paste. Upload was buried three menus deep, download had no button at all, and
  neither is much use to someone who cannot drag and drop. Upload takes **several
  files at once**.
- The preview window's text was rendering in an oversized, yellow, underlined
  debug style on desktop and in the Web UI. Phones were unaffected, which is why
  it survived this long. It is ordinary text now — including the file name, the
  online-only notice and any playback error.

## Notes

- Windows builds are signed; macOS builds are Developer ID signed and notarized.
- Thanks to both reporters. The Web UI downloads were found because one of them
  sent their sync client's own activity log alongside the screenshot.
